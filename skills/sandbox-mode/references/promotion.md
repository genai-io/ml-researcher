# Promotion from sandbox to real — the procedure

There is **no rename / no migration** command. The pipeline must be re-run under non-sandbox conditions for any sandbox result to become authoritative.

## The steps

1. `/sandbox off`
2. `/exp new <same-name-but-real>` — register a NEW experiment with its own EXP id
3. Run it for real (real data, real training, real metrics)
4. Optionally delete the `[SANDBOX]` row from `experiments/ledger.tsv` to keep history clean (but the trial_trace entry should stay as audit evidence that scaffolding was done)

## Why no rename

If sandbox runs could be promoted by file rename / flag flip, the entire enforcement model collapses — every result becomes plausibly tainted. The hard wall (sandbox runs and real runs share no artifact paths or hashes) is what gives the critic agent a clean signal to enforce on.

## What carries over and what doesn't

Carries over:
- The pipeline shape (train.py structure, config.yaml fields, ledger schema)
- Code in `train.py` and any helper modules — these are normal code, not "sandbox artifacts"
- Plot / figure rendering logic in `scripts/figure_render.py`

Does NOT carry over:
- `metrics.json` from a sandbox run (always regenerated by the real run)
- `predictions_*.csv` from a sandbox run
- Any figure in `experiments/EXP<id>_<name>_sandbox/figures/`
- Ledger rows tagged `[SANDBOX]`

## When the sandbox run revealed a bug

Often the sandbox scaffold catches a real bug (wrong split path, broken metric grep convention, missing seed). Fix the bug in code, commit, then run the REAL experiment from the fixed state. The sandbox run's role is over once the bug is fixed — don't keep iterating on the sandbox to "make it pass" before switching to real.
